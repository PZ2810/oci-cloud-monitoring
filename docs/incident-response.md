# Incident Response Runbook

This document provides step-by-step procedures for responding to alerts generated by the monitoring stack.

---

## 🔥 Alert: HighCpuUsage / CriticalCpuUsage

**Severity:** Warning (>80%) / Critical (>95%)

### Triage Steps

1. **Check which process is consuming CPU:**
   ```bash
   # SSH into the instance
   top -o %CPU -b -n 1 | head -20

   # Or more detail:
   ps aux --sort=-%cpu | head -15
   ```

2. **Check if it's a container or host process:**
   ```bash
   # View per-container CPU in Grafana or:
   docker stats --no-stream
   ```

3. **Check if it's the keepalive cron (expected behavior):**
   ```bash
   pgrep stress-ng && echo "Keepalive is running — this is expected" || echo "Not keepalive"
   ```

### Resolution

| Cause | Action |
|---|---|
| `stress-ng` keepalive cron | No action — wait 30 min for it to stop. Consider silencing this in Alertmanager. |
| Runaway container | `docker restart <container-name>` |
| Crypto miner / unknown process | `kill -9 <PID>`, investigate how it got there, check SSH authorized_keys |
| Legitimate load | Consider scaling up the instance or optimizing the workload |

## 🔥 Alert: HighMemoryUsage

**Severity:** Warning (>85%)

### Triage Steps

1. **Check memory breakdown:**
   ```bash
   free -h
   ```

2. **Find the top memory consumers:**
   ```bash
   ps aux --sort=-%mem | head -15
   ```

3. **Check container memory usage:**
   ```bash
   docker stats --no-stream --format "table {{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}"
   ```

### Resolution

| Cause | Action |
|---|---|
| Prometheus using too much RAM | Reduce `--storage.tsdb.retention.time` or restart Prometheus |
| Grafana memory growth | Restart Grafana: `docker restart grafana` |
| OS page cache | Usually fine — Linux uses free RAM for cache. Check `available` in `free -h` |

## 🔥 Alert: DiskSpaceLow / DiskSpaceCritical

**Severity:** Warning (>80%) / Critical (>90%)

### Triage Steps

1. **Check disk usage:**
   ```bash
   df -h /
   ```

2. **Find large files:**
   ```bash
   sudo du -sh /var/lib/docker/* | sort -rh | head -10
   sudo du -sh /var/log/* | sort -rh | head -10
   ```

3. **Check Docker disk usage:**
   ```bash
   docker system df
   ```

### Resolution

| Cause | Action |
|---|---|
| Docker images/volumes | `docker system prune -af --volumes` (⚠️ removes unused data) |
| Old log files | `sudo journalctl --vacuum-time=3d` |
| Prometheus data | Reduce retention: `--storage.tsdb.retention.time=7d` and restart |

## 🔥 Alert: InstanceDown

**Severity:** Critical

### Triage Steps

1. **Check if the container is actually down:**
   ```bash
   docker compose ps
   ```

2. **Check container logs for crash reason:**
   ```bash
   docker compose logs <service-name> --tail=50
   ```

3. **Try restarting the failed service:**
   ```bash
   docker compose up -d <service-name>
   ```

### Resolution

| Cause | Action |
|---|---|
| Container OOM killed | Check `dmesg | grep -i kill`, increase Docker memory limits |
| Config error | Check logs, fix config, run `make validate`, restart |
| Docker daemon issue | `sudo systemctl restart docker` |

## 🔥 Alert: ContainerHighCpu

**Severity:** Warning (>80%)

### Triage Steps

1. **Identify which container:**
   The alert label `{{ $labels.name }}` tells you which container.

2. **Check what it's doing:**
   ```bash
   docker top <container-name>
   docker logs <container-name> --tail=50
   ```

### Resolution

| Cause | Action |
|---|---|
| Prometheus compaction | Normal during TSDB compaction — wait |
| Grafana rendering | Reduce dashboard refresh rate or panel count |
| cAdvisor overhead | Known issue — consider resource limits |

## General Escalation Path

1. **Check dashboards** — Grafana at `http://127.0.0.1:3000`
2. **Check raw metrics** — Prometheus at `http://127.0.0.1:9090`
3. **Check alert state** — Alertmanager at `http://127.0.0.1:9093`
4. **SSH to instance** — Run the diagnostic commands above
5. **If instance is unreachable** — Check OCI console, the instance may have been reclaimed
